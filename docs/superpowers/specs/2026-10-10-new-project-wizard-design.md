# New-project wizard — create and freeze a project from the portal

**Date:** 2026-10-10. **Branch:** `research-portal`. **Status:** design, awaiting operator review.
**Replaces:** the disabled "+ New project" button (`web/src/components/Shell.tsx`) and the English-only boards
`docs/design/portal/v2/V2NewProject.html` and `V2NewStart.html`, which stay as reference.

`CLAUDE.md` overrides everything here. In particular: the engine holds no domain knowledge (invariant 4); a
question registry is a dated version (invariant 5); the acquisition floor has no override (invariant 3); source
class travels with every item (invariant 6). Unknown is `null` and "—", never 0.

## Why

A project is three input files written by hand under `projects/<name>/`. That is the first thing a new user
cannot do, and it is where the protocol is decided. The wizard lets an authenticated operator describe a topic,
ask questions, declare the sources and the bar, and create a **frozen** project, while explaining at every step
what Claimstone will do with what was entered. It is the first thing a new user meets, so it is bilingual
(Italian and English) from the start.

## Scope

**In (stage 1):** draft ledger; control routes; a project builder in the engine; templates as data; the wizard UI
(four steps); the i18n infrastructure; contract, decision entry, guide and website pages.

**Out:** opening a round; binding a flow (`flow create`; it binds a round that does not exist yet, so it
belongs to stage 2); authorizing or starting any network or model work; editing an existing project
(a protocol change is a dated bump through its own flow, not this wizard); year or language filters (the engine
filters by host, API and venue only, so the wizard does not show a control that does nothing); any semantic
judgement of a question's wording.

## Architecture

```
browser (web/)                control server (claimstone/control.py)            engine (claimstone/)
  /new/:draft/:step  ──POST──▶  new-project routes ──▶ wizard_drafts.jsonl       project_builder.py
  explanation panel  ◀─GET───   preview (offline)  ──▶ figures (server-computed) ─▶ templates/ (data)
  confirm            ──POST──▶  create ──lock──▶ validate ▶ render ▶ write ▶ projects/<name>/
```

### The draft ledger

`store/_new-projects/wizard_drafts.jsonl`, append-only, in the style of `drafts.jsonl`. One row per save:

| field | meaning |
|---|---|
| `wizard_version` | `1`, registered as an instrument |
| `event` | `step_saved`, `discarded`, `created`, `create_failed` |
| `draft_id` | random 128-bit id, generated by the server |
| `step` | 1–3 for `step_saved`, otherwise null |
| `revision` | integer, +1 per row of this draft; a save names the revision it was based on |
| `data` | the step's normalized content (not YAML text), or null |
| `project` | the project name once chosen, else null |
| `actor`, `signer_auth` | operator id from the session; `"portal-session"` |
| `code_revision`, `recorded_at` | as in every control ledger |

The state of a draft is the latest row per (`draft_id`, `step`). A draft belongs to the operator who created it
and is never listed to another. Nothing in this ledger is read by any stage, profile, verdict or export.

### Routes (all under `/control/v1/`, all POST rules of `control_api.md` apply)

- `POST new` → `{draft_id, revision: 0}`.
- `POST new/{id}/steps/{n}` with `{base_revision, data}` → 422 with field paths when invalid and nothing written;
  409 `STALE_REVISION` when `base_revision` is behind; otherwise `{revision, data, figures}`.
- `POST new/{id}/advanced` with `{files: {…}}` replaces the generated text of a file; it must pass the same
  loaders, and may add to the excluded hosts but never remove one the template declares.
- `GET new` lists the operator's drafts; `GET new/{id}` reads one; `GET new/{id}/preview` → figures only,
  computed offline, no network, no write.
- `POST new/{id}/discard` appends `discarded`.
- `POST new/{id}/create` with `{confirm: true}` and an `Idempotency-Key`.

Every route is registered in `ROUTES`, so the anonymous-access test covers it the moment it exists.

### The project builder (`claimstone/project_builder.py`)

No domain knowledge. It takes the normalized draft and a template (data) and:

1. validates each step with the same loaders as `claimstone validate`;
2. renders `topics.yaml`, `questions.yaml` and `sources.yaml` with a fixed serializer, never by string
   concatenation;
3. writes them to a temporary directory beside `projects/`, loads them with `config.load_project`, and
   requires the loaded protocol to equal the preview's;
4. renames the directory to `projects/<name>/` (atomic; refused if it exists);
5. registers the three files' sha256 in the draft ledger (`created`).

At creation it sets `registry_version: 1` and `frozen_at` to today; `floor_version: 1`, `floor_set_at` to today
and `floor_rationale` to the operator's text (required, never defaulted).

**Name:** `^[a-z0-9][a-z0-9-]{1,62}$`, used only as a directory name after the check, re-checked under the
project writer lock at creation.

**The write path is narrow.** `create_project` is the only code that writes under `projects/`. It creates a
directory that did not exist and never modifies a file of an existing project. A test hashes every existing
project before and after every route and requires no change. The control service's `projects/` mount changes
from read-only to read-write for this reason alone, and `compose.yaml` and `control_api.md` say so.

**Templates** live in `templates/project/<id>/` as YAML data (class definitions with their `assign_when` rules
and roles, default gate thresholds, the excluded-hosts list, a default `extraction` vocabulary).
They are examples of a field's conventions, not engine knowledge. The first is derived from
`projects/example-news-and-returns`; the engine reads them as input and a project in an unrelated field can ship
its own.

## The four steps

Each step saves only a draft. **After saving**, the server validates and stores; nothing runs. **At creation**
and **after start** describe what happens later, so the user never has to guess.

| Step | Inputs | Server checks | Figures shown | What the panel says |
|---|---|---|---|---|
| **1 · Topic** | project name; description (optional, kept in a top-level `description` key of `topics.yaml`, which the protocol digest does not read: proven by a test); topics with label and search terms | name valid and free; ≥ 1 topic; unique topic ids; each topic ≥ 1 non-empty term | topics, terms | Terms **find** works; they do not define what is learned. At creation each term becomes one query per selected index. Widening a topic cannot by itself change a verdict |
| **2 · Questions** | questions: id (automatic Q01…), text, kind | non-empty text; unique ids; kind in the engine's list; **structural checks only** | questions, by kind, with and without a verdict | Each kind is judged by its own rule. `operational` questions are tracked and **never receive a verdict**. At creation the registry is frozen at version 1; changing it later is a dated version bump |
| **3 · Sources and rigour** | source classes from the template; acquisition floor and its rationale; supplied copies (`count` or `separate`); search indexes (`openalex`, `crossref`, `arxiv`); the field's notation (`extraction.value_labels`); Advanced | floor in (0, 1]; rationale non-empty; classes known; excluded hosts ⊇ the template's; `supplied_copies` declared; all loaders pass | classes, floor, searches (= terms × indexes, the rule of `operations.plan_batch`), requests "—" | Below the floor no verdict is produced, and there is no override. Every source carries its class. Excluded hosts are never contacted. Whether supplied copies count toward the floor is declared now and cannot change under this protocol |
| **4 · Review and create** | confirmation | the whole draft rechecked | all of the above | What is created: three files, protocol v1, recorded hashes. What does **not** start: searches, copies, paid model calls. What comes next (stage 2): authorize an exact plan; Claimstone searches, obtains legal copies, prepares documents, annotates, reviews independently, and builds an evidence profile; **a person reads and signs**. The "Start" button is visible and disabled |

The explanation copy is a catalog (`wizard.step<N>.afterSave`, `.atCreation`, `.afterStart`) in both languages,
with placeholders for the figures. A figure the server cannot know arrives as `null` and renders "—".

## Frontend

Routes: `/new` (the operator's drafts: resume or discard; "new draft") and `/new/:draft/:step`. The sidebar
button is enabled for a signed-in operator; without a session the page asks to sign in and shows no form.

Components: `WizardShell` (rail, responsive at 900 px), `StepTopic`, `StepQuestions`, `StepSources`, `StepReview`,
`ExplainPanel`, `AdvancedYaml` (a text area; the browser never parses YAML, the server returns errors with a
field path), `ErrorSummary` (focused on failure). Unsaved edits are kept in the page and a leave-warning is
shown; a refused save keeps what was typed. `control.ts` gains typed functions; `gen:types` regenerates
`api-types.ts` from `portal-api.schema.json`.

### i18n

`web/src/messages/en.json` and `it.json`; `t("key", {params})`; a language selector in the sidebar footer, initial
value from the browser with English as the fallback, remembered in `localStorage` inside `try/catch`. Tests:
every key exists in both locales; placeholders match; text typed by the user (project name, topics, terms,
questions, rationales) never passes through `t()`. Contract tokens (`SUPPORTED`, `effect`, `operational`, …) stay
canonical and always visible, with the gloss beside them, never instead. The engine is untouched by translation.

## Errors and invariants

- **Invalid step:** 422 with field paths; nothing written; the browser keeps the typed text.
- **Two tabs:** a stale `base_revision` is 409; the page shows the difference.
- **Session expiry:** drafts live on the server and resume after sign-in.
- **Create twice:** the same `Idempotency-Key` returns the first answer; a name taken meanwhile is 409.
- **Create interrupted:** the temporary directory is removed; the rename is atomic, so everything exists or
  nothing does; a failure appends `create_failed` with its reason.
- **Round trip:** the files are reloaded with `load_project` and their protocol must equal the preview's.
- Invariant 4: the builder contains no field-specific value; invariant 5: version 1 with a date, the registry
  digest recorded; invariant 3: a floor with its rationale and no override; invariant 6: a class is required.
- **Privacy:** the project is created under `projects/`, which is gitignored; the wizard says so at creation.
- **Nothing runs:** no route here starts a stage, a network request or a model call, and `control_api.md`'s
  "never runs stage commands" stays true.

## Tests

- **Engine:** draft → files → `load_project` round trip; the digest equals the preview's; a `description` key
  leaves `protocol_sha256` unchanged; `kind` is required by the wizard though the loader permits it empty;
  excluded hosts cannot shrink; every template loads.
- **Routes:** session, CSRF, Origin, size, unknown keys, idempotency, 409s (stale revision, name taken),
  anonymous access over the registry; **no route changes any existing project** (hash before and after).
- **Frontend:** step navigation, error summary, the 900 px breakpoint, "—" for `null`, locale parity, user text
  never translated, the rule that only `control.ts` makes non-GET requests still passes.
- **Live check:** create a throwaway project from the example template into a temporary `projects/` and run
  `claimstone validate` on it.

## Known gaps, stated here rather than hidden

- Year and language filters are absent in the engine, so absent in the wizard.
- A vague question is not detected; the wizard offers a static note on how to write one.
- Flow binding and the exact plan preview (requests, cost) belong to stage 2.
- The explanation copy of every step is written in the plan, in both languages, and reviewed with the operator.
